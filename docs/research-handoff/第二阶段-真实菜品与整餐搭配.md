# 第二阶段：真实菜品，再组成整餐（待第一阶段返回并复核后派发）

本文件是后续任务范围；这次先派发第一阶段食材研究，不让同一轮调研跳过基础数据直接编食谱。

## 输入

第一阶段返回并复核的食材参考库、七目标食养原则、数据缺口和旧规则审计结论。未解决的数据缺口继续保留，不能用菜谱名称掩盖。

## 数据关系

食材 → 真实菜品 → 整餐搭配。

- 食材：番茄、鸡蛋、食用油、盐等，各自有形态、数值与证据。
- 菜品：番茄炒蛋，具有多个原料、实际做法、总份数、每份份量、油盐酱料，以及不同目标下的条件评估。
- 整餐：主食加一道或多道菜，组合后重新评估整餐数据与目标冲突；一道菜本身不等于一顿完整的饭。

上述名称仅用于解释数据关系，不预先宣称菜品对某种疾病适宜。

## 菜品要求

1. 选择现实中常见、用户愿意吃、家常或常见外卖场景能找到的菜式；覆盖不同原料、口味和烹调方式。种类不足时报告缺口，不靠改名凑数。
2. 禁止以“清炒/清蒸/少油煎炒”机械拼接单一食材名来制造菜品。菜品须有可追溯的名称与真实配方。某个菜名少见不等于绝不存在；判断应依据实际来源。
3. 菜品存在和做法可参考专业出版食谱、医院/营养科配方或可信的原始烹饪资料。菜谱平台的原作者配方可作为烹饪出处，不能作为疾病适宜性的医学依据。
4. 分开标记“原文配方”和“为健康目标调整的版本”；少油、少盐、不加糖等修改需要明确，不能沿用原配方的营养总数。
5. 每道菜记录唯一 `dish_id`、标准名称与别名、菜品类型、全部食材及对应 `food_id/form_id`、用量/生熟/可食部、调味料、做法、份数、成品重量或其未知状态、每份数据、过敏原、替换条件及引用。
6. 每道菜对七个目标分别评估，医学判断的证据链为食材/用量/做法/食养原则；原文直接支持与依据原则推断要区分。不能把“有鸡蛋”或“有番茄”当作整道菜适宜性的证明。
7. 未知油盐、商家酱汁或烹调损失时标记不完整；不能按0计算并输出完整营养总数。

## 整餐与选餐

菜品库完成后再组合早餐、午餐、晚餐候选，目标为每餐至少9种有实际区别的完整搭配。使用 `meal_id` 引用一份主食及一道或多道 `dish_id`，记录每道菜取用的份数。

整餐需要重新核算数据、食材重复、份量和目标冲突。菜品里已有番茄、鸡蛋、油盐时，不在整餐中重复计算同一份原料。食材或菜品替换后重新计算和核查过敏原，不能声称自动等效。

同时研究如何在真实菜品中先排除不喜欢或禁忌食材，再优先推荐用户喜欢的菜式。不要把菜式固定为三餐唯一答案；给用户可选的实际菜品组合。

## 后续交付约定

返回菜品报告、独立菜品库与引用菜品的整餐库，全部保留来源、缺口和 `not_clinically_reviewed` 标记。正式JSON Schema将在第一阶段结果返回后按实际食材数据确定；不能套用第一阶段仅包含食材的Schema。
