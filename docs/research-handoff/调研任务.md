# 第一阶段：全部健康目标的食材数据与食养依据调研（v2）

你是一名执行医学文献检索、营养数据核查和结构化整理的研究助手。请执行本阶段任务，交付有出处、可复核、可保存在本地的食材参考资料。结果仍属于研究参考，不能自称已经过营养师或临床审核。

## 1. 背景与本阶段边界

我们开发了一款中文桌面健康助手，支持健康目标、饮水记录、食物喜好/禁忌和翻牌选餐。当前已有85条食材记录，其中66条参与搭配，数量已经较丰富。本轮优先核实数据和适用条件，不以新增食材数量为成绩。

研究按以下顺序推进：

1. 本阶段：食材本身、不同形态的营养数据、与全部健康目标的关系、旧规则审计。
2. 下一阶段：基于已复核食材建立真实菜品，再由菜品组成整餐候选。

本次不提交完整菜谱、不凑早中晚各9份餐食，不用“烹调前缀＋食材名”生成菜名。当前软件存在把单一食材拼成“清炒番茄”一类标题的问题，下一阶段需要转为番茄炒蛋等有真实配方、完整组成的菜品。本阶段先为这种复合菜提供可靠的食材底座；提到番茄炒蛋仅说明产品需要，不代表对任何疾病已经作出适宜性判断。

必须读取两个附件：

- `health-food-baseline.json`：当前85条食材、ID、旧数值、过敏原映射及17条待审计规则。所有旧数值、标签、解释和规则均是核对对象，不构成医学依据。
- `health-ingredient-reference.schema.json`：本阶段返回JSON的v2格式约束。请使用此版，旧v1的27份餐食交付要求已取消。

缺少附件时先说明，不能假装已经逐条审计。

## 2. 全部七个目标必须分别调研

七个目标是并列研究范围，不以痛风研究代替其他目标，也不把高血压、糖尿病仅作为痛风的附带条件。

| 目标ID | 软件目标 | 需要独立检索和核查的维度示例 |
| --- | --- | --- |
| `uric` | 高尿酸、痛风相关食养 | 嘌呤数值与结局证据的区别、动物/植物来源、病期、份量、酒精和糖相关证据 |
| `pressure` | 高血压相关食养 | 钠、盐和酱料的换算、含钾食材的适用条件、不同加工方式与合并疾病限制 |
| `glucose` | 糖尿病、糖尿病前期相关食养 | 碳水定义与含量、纤维、整食/果汁、生熟加工、份量；GI和整餐反应的区别 |
| `lipids` | 血脂异常相关食养 | 总脂肪与脂肪酸构成、胆固醇、纤维、加工和烹调影响 |
| `weight` | 体重管理、超重肥胖相关食养 | 能量、营养密度和份量；食材本身与个体能量需求的区别 |
| `liver` | 脂肪肝相关食养 | 独立适用范围、能量和糖相关证据、酒精及合并情况；不能只复用“减重”标签代替检索 |
| `general` | 一般成年人均衡饮食 | 食物多样和合理搭配，检查是否误用了特定疾病才需要的限制 |

这些维度是待研究问题，不是已经确立的医学结论。每个目标都要给出独立的来源、适用人群、发现、限制与缺口。对于同时具有多个目标的人，另报告规则冲突和需要个体化确认的情形。

明确肾功能异常/透析、心衰或限水、孕哺期、未成年等是否超出通用参考范围。尿酸相关建议需区分无症状高尿酸、急性发作、间歇期和慢性痛风；其他疾病也要按原文保留必要的分型/治疗阶段限制，不自行推断个体处方。

## 3. 证据与检索要求

必须实际检索、阅读资料。优先使用现行政府/卫生机构指南、正式标准、专业学会指南、权威食物成分数据库、系统综述和同行评议原始研究。为每个目标独立检索，核对版本与替代情况。博客、商家宣传、AI回答和搜索摘要不能作为医学判断的最终依据。

可以从以下官方入口开始，但不能只检索这些资料：

- [国家卫健委2023年食养指南发布页：含高血压、糖尿病、高脂血症](https://www.nhc.gov.cn/sps/c100088/202301/f01895a06c5349ef999f25da833c166d.shtml)
- [国家卫健委2024年食养指南发布页：含高尿酸/痛风、肥胖](https://www.nhc.gov.cn/sps/c100088/202402/9ba512ba8e314a47a181db11d2fa188d.shtml)
- [国家卫健委2024年慢性病营养和运动指导原则发布页](https://www.nhc.gov.cn/ylyjs/gzdt/202407/256b4eb8398440a8811344c7be50a333.shtml)

脂肪肝和均衡饮食也要独立寻找相应的权威来源，不能因为上面未列出就略过。

每个来源记录标题、发布机构/作者、原始年份/版本、URL、检索日期、全文访问情况和适用性。不要把转载、网页迁移或抓取时间当作原始发布日期。未读到全文时明确标为摘要可见或无法访问，不能声称核对了全文表格。转载不算独立证据。

每项营养数值、每条原则和每个适用性判断必须有对应引用，定位到PDF页码/表号/条款、网页小节或数据库条目编号。不是只在文末列参考书目。保留原文直接支持、研究者推断和冲突证据的区别；同一食物不同来源有差异时并列保留并解释，不任意平均，不只选择符合旧程序的值。

## 4. 食材研究要求

1. 保留全部85条原始 `food_id`，包括目前被排除的食材；找不到数据也保留该ID，并写明检索缺口。优先处理66条可选食材。
2. 现有种类较丰富，先核实。仅在下一阶段真实烹饪确有需要时补充基础调味食材，如盐、酱油、常用油或淀粉，并解释新增原因；新增ID用 `new_` 前缀。
3. 区分品种、动物部位、鲜/干、加工和生熟状态、可食部。不同形态使用独立 `form_id`。不能将生食物的蛋白、熟食物的嘌呤和另一品种的钠拼成一个代表值。
4. 数值使用每100g或每100ml口径，并标明定义和单位。无密度依据时不能把ml等同于g；无可靠依据时不能自行换算“一个/一片”的克数。
5. 嘌呤与尿酸当量、总碳水与可利用碳水、总糖与添加糖、钠与食盐均要区分。GI若有数据需说明参照物和测定/烹调条件，不能由含糖量推算，也不能直接当作一餐的血糖反应。
6. 可收录能量、蛋白、碳水、纤维、脂肪、饱和脂肪、胆固醇、钠、钾、糖、嘌呤等有依据的数据。并非要求每个食物每项都填满。无数据用 `null`，不能填0；不伪造精确数值或等级。
7. 每种食材都必须分别回答七个目标。允许“有条件兼容”“限制”“避免”“来源没有专门讨论”“证据不足”，但不能因为低嘌呤就标记所有目标均适合。未专门讨论不等于安全证明，也不等于禁食。
8. 每个判断保留适用人群、具体食材形态、原因、份量依据、条件、烹调影响与来源。份量没有依据就留空，不强制给一个通用克数。
9. 核查常见过敏原及派生食材映射，尤其鱼类、鸡蛋蛋白与整蛋、嫩豆腐与大豆、乳制品、含麦食材和调味料。原料过敏原与生产/餐饮交叉接触分开描述，不凭菜名保证无过敏原。

## 5. 旧规则审计

逐条审计附件17条规则，给出支持、部分支持、不支持、证据冲突或未找到证据的结论，以及保留、修订、删除、个体化或暂缓的建议。结论必须有依据，不为旧程序寻找背书。

尤其核查：统一每日300mg嘌呤、35ml/kg饮水、统一蛋白目标、固定120g主食、0–3果糖等级、用少数食材排除代替控钠/调脂、体重和脂肪肝目标只加全谷物权重，以及对普通人也沿用疾病限制的问题。

## 6. 返回文件与格式

交付两份UTF-8文件：

**`ingredient-research-summary.md`**

中文报告，分别说明七个目标的来源、主要发现、适用边界、冲突和缺口；列出食材及规则审计覆盖率、应改动的旧规则、需要专业确认的内容，以及供第二阶段使用的准备情况。不得用一句“兼顾其他疾病”替代其他六个目标。

**`health-ingredient-reference.json`**

严格符合附件v2 Schema。根字段固定为：

`schema_version`、`meta`、`sources`、`goal_summaries`、`principles`、`foods`、`rule_audits`、`gaps`。

固定 `schema_version` 为 `2.0.0`；`meta.research_stage` 为 `ingredients`；`meta.status` 为 `research_reference_only`；`meta.review_status` 为 `not_clinically_reviewed`。`meta.goal_scope` 必须包含全部七个目标且不重复。

- `goal_summaries` 必须有七个目标各自的对象，每项给出覆盖情况、适用人群、检索问题、发现、限制和引用。
- 每条 `foods` 必须包含 `goal_assessments`，其中同样必须有七个目标各自的对象，不能缺项。
- `sources` 使用唯一 `SRC_` ID；`principles` 使用唯一 `RULE_` ID；食材沿用已有ID，形态使用唯一 `form_id`。
- 每个数值有独立定义、来源类型和定位引用；字段与枚举不得自行改名。未知为 `null`，缺项写进 `gaps`。
- 每个来源ID、原则ID和形态ID的引用都要能找到对应记录。`form_ids` 应引用本食材的形态。
- 覆盖不足就标记 `partial` 并说明检索过什么、还缺什么；不宣称已完成专业审核。

提交前验证JSON语法和Schema，并检查85个食材ID、七目标全覆盖、17条规则、重复ID、悬空引用、单位、生熟口径和直接证据/推断的区分。不能出现注释、尾逗号、NaN、Infinity、占位符或省略号。

本阶段不要增加 `recipes`、`dishes` 或 `meal_plans` 字段。不要越过食材核实直接生成完整菜谱。

无法联网、没有读到原文或不能完成时，如实返回部分成果和缺口。若不能附文件，分别返回完整Markdown和JSON代码块；内容较长时按完整数组分批输出并给出合并说明，不能截断在对象中间。
